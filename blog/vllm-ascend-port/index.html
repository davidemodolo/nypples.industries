vLLM on Ascend: Porting an Open-Source Inference Engine to CANN 8.0.

Research April 18, 2026 · 17 min read

The vLLM community’s Ascend adapter is a remarkable piece of open-source engineering — it maps CUDA kernels to CANN operators with surprisingly low overhead. But the port isn’t complete. Here’s what we maintain in our fork, what we patched, and what still needs work.

Why vLLM?

When we started Nypples, we had a choice: build a custom inference engine on MindSpore, or adapt an existing open-source engine. vLLM was the obvious answer. Its PagedAttention memory management, continuous batching, and OpenAI-compatible API server are battle-tested across hundreds of production deployments.

The vLLM Ascend adapter — maintained primarily by Huawei engineers with community contributions — replaces CUDA kernels with CANN (Compute Architecture for Neural Networks) operators. The architecture is clean: a plugin system that intercepts CUDA calls and routes them to CANN equivalents. For most operations (matmul, layer norm, activation functions), the mapping is one-to-one and performs at parity.

For operations that don’t have a direct CANN equivalent — flash attention, grouped-query attention, and certain fused CUDA kernels — the adapter falls back to a shim layer that decomposes the CUDA kernel into multiple CANN operators. This works, but the overhead is measurable.

Our fork’s divergence from upstream

We maintain 7 patches on top of the upstream vLLM Ascend adapter (version 0.8.3 as of July 2026). Six of these are already contributed back and merged. The remaining one — a CANN memory allocator optimization for MoE models — is in review.

PagedAttention on Ascend

PagedAttention is vLLM’s killer feature — it manages KV-cache memory in non-contiguous blocks, eliminating the memory fragmentation that plagues traditional inference engines. Porting it to Ascend was nontrivial because CUDA’s virtual memory management (via cuMemMap) has no direct CANN equivalent.

The adapter implements PagedAttention using CANN’s dynamic memory pool, which achieves similar results through a different mechanism. The performance comparison:

MetricCUDA PagedAttention (A100)CANN PagedAttention (Ascend 910C)
KV-cache memory overhead2.3%3.8%
Block table lookup latency4.2 μs5.1 μs

Memory fragmentation after 10K requests1.1%2.4%

The CANN implementation has slightly higher memory overhead (+1.5pp) but supports larger batch sizes thanks to the 64 GB HBM2E per card vs. A100’s 80 GB but with a wider memory bus. The tradeoff is real but acceptable.

The road to full upstream parity

We track three remaining gaps between our fork and what we’d consider full upstream parity:

  1. Speculative decoding. vLLM supports draft-model speculative decoding on CUDA via cudaStream priority scheduling. CANN supports stream priorities but the adapter hasn’t wired them through yet. Target: Q4 2026.
  2. FP8 attention kernels. CANN 8.0 supports FP8 matrix operations, but the attention kernel implementations lag behind CUDA’s FlashAttention-3. Huawei is actively working on this. Target: Q1 2027.
  3. Multi-node tensor parallelism scaling. Beyond 8 nodes, HCCL collective operations show scaling inefficiencies that NCCL solved years ago. This is the hardest gap to close because it’s a collective communication library problem, not an adapter problem. Target: Q2 2027.

What this means for users

If you use the OpenAI Python SDK pointed at our endpoint, you don’t see any of this. The API is identical. The patches, the shim layers, the CANN memory allocator — they’re invisible. You get a /v1/chat/completions response with the same JSON schema, the same latency profile, and one important difference: your data never left Italy.

That’s the promise of the vLLM Ascend adapter. Not that Ascend is better than CUDA (it isn’t, yet), but that it’s good enough that you don’t need to care what hardware is underneath. The open-source community has done the hard work of abstracting the silicon away. We’re just helping finish the job.
